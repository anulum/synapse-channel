# Crypto agility

Synapse signs with Ed25519. A signature suite interface lets a signer change
algorithms without changing its callers, and a hybrid post-quantum suite
protects long-lived audit logs today.

## Suites

| Suite | Public key | Signature | What each part signs |
| --- | --- | --- | --- |
| `ed25519` | 32 bytes | 64 bytes | the domain, a NUL byte, then the message |
| `ed25519+ml-dsa-65/v1` | 32 bytes Ed25519, then 1952 bytes ML-DSA-65 | 64 bytes Ed25519, then 3309 bytes ML-DSA-65 | the composite preimage |

The composite preimage is the label, the suite name, the domain and the message,
each followed by a NUL byte except the last:

```text
SYNAPSE-COMPOSITE-SIG-v1 \0 ed25519+ml-dsa-65/v1 \0 domain \0 message
```

ML-DSA-65 also takes the domain as its FIPS 204 context.

- **Both halves must verify.** A wrong length, a swapped order, or one half
  alone is refused.
- **Neither half stands alone.** Each half signs the composite label and the
  suite name, so it is never a valid signature over the plain domain
  preimage of a single-algorithm suite. The label itself is refused as a
  domain, so no Ed25519 preimage can begin like a composite one.
- **Keys stay in their suite.** A key file names its suite, and loading it for
  any other suite is refused.
- **The version is in the name.** Changing the encoding, for example to the
  final IETF composite encoding, will be a new suite name, never a change to
  this one.
- **ML-DSA must be available.** It comes from the installed `cryptography`
  backend. Synapse probes for it at import, and a backend without it leaves
  every other command working. Only selecting the hybrid suite is refused,
  and the refusal names the missing algorithm.

The vectors are in `tests/fixtures/signature_suite_v0_1.json`, checked with
`tools/signature_suite_vectors.py --check`. ML-DSA signing is hedged, so the
vectors are verified, not regenerated byte for byte.

## Protecting a log against a future break of Ed25519

A signed tree head commits to every receipt of a log up to its size. To anchor
those receipts in a post-quantum signature, countersign each tree head with a
hybrid key while Ed25519 is still sound. See
[Verifying AEF evidence offline](aef-verification.md#6-a-post-quantum-countersignature-of-a-tree-head)
for the commands. Once Ed25519 is broken, the receipts up to the countersigned
size remain authentic for an export whose root matches the countersigned root.

A countersignature has two limits:

- It proves endorsement by the post-quantum key holder, at a time it does not
  prove.
- The countersigner checks the head with Ed25519, so a countersignature made
  after a break may endorse a forged head.

Countersign routinely, for example with every exported tree head, and keep the
countersignatures in custody independent of the log host.

## What is not covered yet

Receipts, frames, policies, identities and tokens are still signed with
Ed25519 only. Moving them onto the suite interface, or accepting hybrid
signatures in them, changes their formats or the wire protocol. That is a later
step, and it needs the project lead's decision. Key exchange does not change.
